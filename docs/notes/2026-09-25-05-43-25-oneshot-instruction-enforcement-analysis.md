# ワンショット指示の強制力分析（判断ポイント数と指示強制カロリーの関係）

> **⚠️ 機密情報保護ルール**
>
> このノートに記載する情報について:
> - API キー・パスワード・トークンは必ずプレースホルダー(`YOUR_API_KEY`等)で記載
> - 実際の機密情報は絶対に含めない
> - .env や設定ファイルの内容をそのまま転記しない

**作成日**: 2026-09-25
**関連タスク**: setup-securecheck v3.1.0のREADME「Node.js前提」ワンショット指示のドラフト作成中の脱線

## 問題

`setup-local`実装後、README用に新しい「Node.js前提でのAIワンショット指示書」を書いた際、判断ポイント（`scan`結果の解釈・`package.json`のマージ）に【判断待ち】マークを入れただけで満足していた。「まだ強制力が足りなさそう」と指摘され、「AIは手順が減っても、手順を守らせる歯止めを明記しないと一気に全部やって手抜きしようとする」という懸念が出た。これをきっかけに、このプロジェクトの`docs/actions/*.md`と`setup-securecheck.md`のウィザード部分に既に埋め込まれている「歯止め」を横断的に分析した。

## 整理: 抽出できた7つの歯止め機構

`doc_note_and_commit.md`・`git_commit.md`・`setup-securecheck.md`のウィザード部分（「🤖 AI への重要な指示」節）を横断して見ると、以下が重ねがけされていた。

1. **初手の理解チェックリスト（チェックボックス）**: 守るべき制約を1項目ずつ原子化して`- [ ]`で列挙させる。一括の相槌より、後から個別に指摘しやすい
2. **明示的なゴーサイン待ち（最初の一手）**: 「理解できましたか？ゴーサインをください。」という質問文で指示書を終える。「待って」という指示ではなく、**会話のターンそのものを切る**という構造的な強制力。agentic環境（1ターンに複数ツール呼び出しを積める）では特に重要
3. **絶対守るべきことの冗長な再掲**: チェックリストとは別に、同じ制約をもう一度独立した見出しで書く。片方が読み飛ばされても残る
4. **良い例・悪い例による失敗モードの具体化**: 「❌ ユーザーの返信を待たずに複数コマンドを連続実行」のように、やってはいけない具体的な行動を名指しする。抽象的な「気をつけて」より、解釈で逃げる余地を塞げる
5. **単位の明示（1コマンド＝1ターン）**: バッチしていい範囲を数値で固定し、「効率化のため複数まとめて」という合理化を防ぐ
6. **実行→報告→提案→待機、の4拍子ループの明文化**: 1回きりの門番ではなく、全ステップに対して繰り返される構造として明記する
7. **判断ポイントの明示マーキング**: 全部が止まるわけではなく、どこが自動実行可でどこが判断待ちかの境界線を引く

## 発見1: Node化が減らすのは判断ポイントの「数」であって、1つを守る強制力の「重さ」ではない

「Node.js化したので指示書も短くシンプルにできるはず」という最初の期待は誤りだった。実際には:

- `install.js`/`scan`/`setup-local`が吸収したのは、確定的チャンク**内部**の揺れ（生コマンドを1つずつ正しい順序で打鍵する際の揺れ）
- しかし判断ポイント（`scan`結果の解釈、`package.json`のマージ）は消えておらず、**1個の判断ポイントを守るための機構（理解チェック・ゴーサイン待ち・悪い例明示・報告ループ）に「弱いバージョン」は存在しない**。守るなら`git_commit.md`と同じフルセットが要る

setup-securecheckの元々の確定的チャンク/判断交互構造（[setup-securecheckの確定的チャンクと3層の証拠構造](./2026-09-23-23-13-19-setup-securecheck-deterministic-chunks-and-evidence-layers.md)参照）に照らすと、判断ポイントは元々4つ（①0.1結果解釈、②スキャン結果解釈、③2.1 scripts追加、④3.2 simple-git-hooks追加）あったが、`install.js`の冪等コピーが①を吸収し、③④は「package.jsonマージ」という同じ作業として1回にまとめられるため、v3.1.0のNode.js前提フローでは実質2つ（②・③④統合）まで減った。**これは本物の進歩だが、各判断ポイントを守る強制力のコストはゼロにならない**。

## 発見2: 「揺れる層」は一枚岩ではなく2層構造だった

README.mdの「四層構造アーキテクチャ」（確実に動く層／揺れる層）に照らすと、「揺れる層」は実は2層に分かれていたことが分かった。

- **判断の中身**（本物の漏洩かどうか、package.jsonをどうマージするか）: 自然言語の意味理解が要るためコード化不可能
- **判断をどこで・どう止めて行わせるかという手続き**: 自然言語で書かれているが、チェックボックス・ゴーサイン待ち・悪い例・報告ループという設計によって、**コードに近い確定性まで持ち上げられる**

`setup-local.js`の`checkPreCommitPrerequisite()`（満たされていなければ具体的なエラーで止める、というコード側のゲート）と、`setup-securecheck.md`の「はいと返信するまで開始しない」（プロンプト側のゲート）は、実装言語が違うだけで**同じ目的（判断ポイントを勝手に通過させない）を果たす対の技法**である。

## 適用

上記を踏まえ、`quickstart.md`（[setup-securecheck v3.1.0 - README再構成・quickstart.md新設・スナップショット分離の記録](./2026-09-25-05-42-25-setup-securecheck-v3.1.0-readme-quickstart-snapshot.md)参照）に、判断ポイント2箇所用に薄めた形で7機構のうち複数（チェックボックス・ゴーサイン待ち・悪い例・判断マーキング・1手順ずつ実行）を反映した。

## 学び

- 「確定的にできる部分を増やす」ことと「残った判断ポイントを守る」ことは別々に投資が必要な軸であり、片方への投資がもう片方を安くしてくれるわけではない
- この分析はsetup-securecheck固有ではなく、**他パターンのワンショット指示書（docs-structure等）にも横展開できる汎用的な知見**だと考えられる

## 今後の改善案

- [ ] docs-structure等、他パターンのワンショット指示にも同様の歯止め機構が必要な判断ポイントが無いか棚卸しする
