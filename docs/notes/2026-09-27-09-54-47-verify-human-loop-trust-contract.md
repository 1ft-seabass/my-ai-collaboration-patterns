## 問題

### 出発点: 信頼契約の話

Windows実機での`install.js`/`setup-securecheck`導入検証がいずれも一発成功し、`install.js`のCREATE/SKIPログ、`setup-local`の`15/15 passed`など、自動化があまりにきれいに完結するようになった。その結果、逆に「AIが実際に何をしたのか」が見えにくくなる、という感覚が生まれた。

これは「AIを疑っている」という不信の話ではなく、**AIの活動を検証可能な状態に保っておく、という信頼契約の話**（信頼するからこそ、検証の手段を残しておく）として持ち出された論点だった。

### 問い

「さっきのログみたいに最終レポートを出させるといいんですかね？AIが嘘をついたりすることはないかな」という問いが出た。これに対しては「いや、AIの自己申告（自然言語の要約）自体が、悪気なく間違えたり話を盛ったりしうるので、喋らせること自体は根本対策にならない」という結論になった。

## 試行錯誤

### アプローチA: ノート＋コミット（既に実践・成功）

**試したこと**: 口頭報告ではなく、「ノート＋コミット」という検証可能な成果物を作業の区切りごとに残す（このセッション中、verify.jsのタイムゾーン修正で既に実践）。

**結果**: 成功。この方針自体はAIの永続メモリにも`feedback_note_commit_as_trust_verification`として記録した。

### アプローチB: 「AIが何をしたか」だけでなく「仕組みが今も壊れていないか」の検証（本ノートの主題）

**試したこと**: 同じ信頼契約の発想を、「AIの活動記録」だけでなく「作られた仕組みそのものが今も機能しているか」にも広げられないか検討。setup-securecheckの`verify`コマンドの立ち位置を再確認した。

**発見**:
- `install.js`/`setup-local`は導入時に一度だけ実行される「点」の作業
- 一方`verify`は、`README.md`の設計思想に既に明記されていた: 「**verify は人間が叩く**（AI が設定 → AI が確認のループを断ち切る）」。`setup-securecheck.md`にも「定期的に`verify --test-run`を実行してください」と明示されている
- つまり`verify`は元々、導入時の「点」だけでなく、その後も人間が継続的に使う「線」の道具として設計されていた

**結果**: 設計思想としては既に存在していたが、`quickstart.md`（Node.js前提の新しい導入手順書）の実際の手順には、この「線」の使い方が反映されていなかった（Step 5の後片付けで手順が終わっており、人間への締めが無い）というギャップが見つかった。

### アプローチC（成功）: quickstart.mdにStep 6を追加

**試したこと**: `quickstart.md`のStep 5（後片付け）の後に、Step 6として以下を追加:
1. **（判断）**: AIが`npm run security -- verify --test-run`を実行し、`setup-local`内部で直接呼んでいた`node .security-check/cli.js verify --test-run`とは別に、package.jsonにマージした`security`スクリプト経由でも同じ結果になるか確認する（npm経由の呼び出し自体はこの時点まで未検証だったため）
2. **締め**: 問題なければ、人間に「ご自身でも一度`npm run security -- verify --test-run`を実行してみてください」「問題なければノート化してコミットすることをおすすめします」と伝えて、バトンを人間に戻す

冒頭のチェックボックス（AIが開始前に提示する手順一覧）にも該当行を追加した。

なお、CIでの自動定期実行は検討しなかった。これは新しい判断ではなく、既存ノート（[フェイルクローズ確認の理解とCIスタンスの整合](./2026-09-23-02-12-53-fail-close-check-and-ci-stance-alignment.md)）に明記された「パターンrepoはCIの設定ファイルを持たない」という既存合意の範囲内での確認だった。

**結果**: 成功。

## 解決策

`quickstart.md`にStep 6（最終確認の判断＋人間への締め）を追加し、`README.md`の設計思想（「verifyは人間が叩く」）と実際の導入手順の間にあったギャップを埋めた。

**実装場所**: `patterns/setup-pattern/setup-securecheck/quickstart.md`

**主なポイント**:
1. 新しい「（判断）」は、既存の2つの【判断】ポイント（scan結果解釈・package.jsonマージ、ユーザーの返信を必ず待つ重い判断）とは性質が異なる。AI自身が結果を見て自己完結できる軽い確認であり、失敗時のみユーザーに報告する（冒頭チェックボックスの「【判断】と書かれた2箇所」というカウント表現は変更していない）
2. 「締め」の文言はAIが要約・言い換えせずそのまま人間に伝える指示にした（AIの解釈を挟まず、決まった言葉で人間にバトンを戻すため）
3. `setup-securecheck.md`（従来のウィザード手順書）側は変更しない（ユーザー判断）。まずは`quickstart.md`だけで様子を見る

## 学び

- 「自動化の質が上がるほど、AIの活動が見えにくくなり不安になる」という現象は、AIへの不信ではなく、検証可能性を保つための信頼契約の問題として扱うと筋が良い
- AIに自己申告のレポートを出させることは、この問題の対策にならない（自己申告自体が誤りうる）。対策は「検証可能な成果物を残す」こと（ノート＋コミット）と「仕組み自体を独立に検証できる手段を用意する」こと（verify）の両輪
- 「点」（導入時に一度だけ）と「線」（その後も継続的に）という区別は、setup-securecheckのようなセットアップ系パターンの機能を設計する際の有効な軸になりそう
- 設計思想（README.md）には既に答えが書いてあることがあり、実際の手順書（quickstart.md）とのギャップを都度確認する価値がある
