# フェイルクローズ確認の理解とCIスタンスの整合

> **⚠️ 機密情報保護ルール**
>
> このノートに記載する情報について:
> - API キー・パスワード・トークンは必ずプレースホルダー(`YOUR_API_KEY`等)で記載
> - 実際の機密情報は絶対に含めない
> - .env や設定ファイルの内容をそのまま転記しない

**作成日**: 2026-09-23
**関連タスク**: [kit構想 Fableセッション原資](./2026-09-22-23-36-08-kit-vision-fable-session-source.md)の3.2節（フェイルクローズ確認をsetup-localから外す決定）の理解を深める会話

## 問題

[kit構想 Fableセッション原資](./2026-09-22-23-36-08-kit-vision-fable-session-source.md)には「フェイルクローズ確認（`--full`）はsetup-localに含めず、パターンリポジトリ側のNodeテストとして1回証明すれば十分」という決定が書かれていたが、この「1回でよい」の意味する時間軸が曖昧だった。ユーザーから「AIが勝手に何かする可能性を考えると、その後も永遠に大丈夫とは言えないのでは」という疑問が出た。

## 調査

### 時間軸の整理（焼き込み/かぶせの軸で考える）

フェイルクローズの振る舞い（gitleaksバイナリが無いときコミットをブロックするかどうか）は`pre-commit.js`という**コードの中身**に宿っている。これは焼き込み層（テンプレートからコピーされ、どの案件・マシンでも同一）の性質であり、「今このマシンにバイナリが実際に置いてあるか」のようなかぶせ層（マシンごとに変わる）の性質とは別物。

| 軸 | 再チェックの要否 | 理由 |
|---|---|---|
| 案件・マシン単位（`setup-local`実行のたび） | 不要 | 焼き込まれた共通コードを信頼してよい |
| パターンリポジトリのコード変更単位（`pre-commit.js`等を書き換えるたび） | **必要（都度）** | コードが変わればその都度壊れうる |

このプロジェクト自身に「確定的に証明したコードでも大規模な書き直しで劣化する」実例がある。`install-gitleaks.js`は2026-06-26に一度`adm-zip`（pure JS）へ修正されたが、v3集約リストラクチャリングでファイルが丸ごと再構成された際にその修正が失われ、PowerShell依存に戻ってしまった（[メンテナンスコストのアーキテクチャ方針合意](./2026-09-22-23-20-37-maintenance-cost-architecture-direction-agreement.md)参照）。フェイルクローズも同種のリスクを持つ。

### 実際のコードを確認した発見

`patterns/setup-pattern/setup-securecheck/templates/.security-check/lib/pre-commit.js`を読むと、フェイルクローズの分岐は**既に実装済み**だった（284-290行目）。

```js
} else {
  // フェイルクローズ: gitleaksが無い状態は「secretlintのみで守られている」半端な状態であり、
  // 気づかれないまま運用が続くこと自体がリスクなので、警告に留めずコミットをブロックする。
  gitleaksOk = false;
  console.error('  ❌ gitleaks が見つかりません — フェイルクローズ方針によりコミットをブロックします');
```

ただしこの分岐は`findGitleaksBinary()`がバイナリを見つけられなかったときにしか通らない。gitleaksが正常に導入されている通常運用（このリポジトリ自身も含む）では、日常のコミットで一度もこの分岐が実行されない。つまり「コードとしては存在するが、実行されずに眠っている」状態であり、ここが壊れても通常運用では誰も気づけない。

一方、同ファイルには**毎コミット自動カナリア自己検証**という別の仕組みが既に実装・稼働している（`gitleaksSelfCheck`/`secretlintSelfCheck`、[per-commit canary self-verification実装ノート](./2026-07-12-08-36-00-per-commit-canary-self-verification-implementation.md)参照）。これは「本物のコミットを試みて、ブロックされた証拠をログに残す」という設計思想で、フェイルクローズ確認と同じ発想だが、対象が異なる。自動カナリアが証明するのは「検出ルールが機能しているか」（gitleaks/secretlintが実際に動いてカナリア文字列を検出できるか）であり、「バイナリが丸ごと無いときにブロックする分岐」自体は対象に入っていない。

### CIスタンスとの整合

[kit構想 Fableセッション原資](./2026-09-22-23-36-08-kit-vision-fable-session-source.md)7.6節「射程の外に置くもの」には次のように書かれている。

> **CI の設定ファイル**: 肥大化する。パターン repo が CI の都合を知り始めると、CI のためのコードが増える → 中のコマンドが素直に CI に等しい状態を保つ。将来 CI に載せたい人はこの2つを呼ぶだけで、リポジトリ側は何も知らない

これは「CI設定ファイル（`.github/workflows/*.yml`等）を持たない」という意味であり、「自動テストを書かない・走らせない」という意味ではない。会話の中で一時的にこの区別を見失い、「CIに頼るかどうか」という誤った二択で考えかけたが、原資には既に明確なスタンスが書かれていた。

このリポジトリ自身、既にsetup-securecheckを自己導入しており（ルート直下に`.security-check/`が存在）、`git commit`のたびに実際にNode.jsコードを実行する自己ホスト型の仕組みが動いている。新しいCI基盤を用意しなくても、この既存の仕組みを拡張すれば、GitHub Actions等を使わずに「コードが変わったら自動で確認する」を実現できる。

## 学び

- 「1回証明すればよい」という言葉は、"何回実行するか" ではなく "どの軸で証明が成立するか"（案件軸 vs コード変更軸）の話として理解すべきだった
- 確定的なコードとして実装されていても、実行頻度が低い分岐（フェイルクローズのような「異常系」）は、通常運用で一度も踏まれないまま劣化に気づけない構造的リスクを持つ。これは`install-gitleaks.js`のPowerShell依存回帰と同型の問題
- 「CI射程外」の原則を、条件反射で「自動テスト全般を避ける」方向に拡大解釈しかけた。原資に書かれたスタンスの射程（設定ファイルを持たないこと）を都度確認せず、雰囲気で判断してしまうと同じ誤読を繰り返しうる
