## セッション文脈サマリー

### 核心的な設計決定

- **決定事項**: setup-securecheckは既存サブコマンドを一切変更せず、`install.js`・`scan`・`setup-local`を追加するのみのマイナーバージョンアップ（3.0.2→3.1.0）とする
  - 理由: 骨子（`.security-check/`構造、`cli.js`という単一エントリポイント、`verify`の15項目契約、`pre-commit.js`の保護ロジック）が不変のため
  - 影響範囲: 既存導入済み案件は明示的に再取得しない限り影響を受けない

- **決定事項**: install.js/scan/setup-localは、手順書全体を俯瞰したときに現れる「確定的チャンク⇄判断」の交互構造の中の、それぞれ異なる確定的チャンクへの命名に過ぎない
  - 理由: この構造を先に把握したことで、「install.jsが全部背負うべきでは」という直感を退け、各スクリプトの責務を明確に線引きできた
  - 影響範囲: 今後新しい確定的チャンクが見つかった場合も、同じ枠組みで命名・実装判断ができる

### 議論の流れ

1. **最初の問題認識**: 前回の合流ノートの「次の一手」が実は起点を誤っていた（トップダウンのkit構想を鵜呑みにし、ボトムアップの方針合意ノートのToDoを汲み上げそこねていた）
2. **検討したアプローチ**: docs-structure側でinstall.jsのパターンを先に確立し、その型をsetup-securecheck側に横展開する。横展開の際、setup-securecheckの複雑さゆえに新しい概念（verify、scan、判断層ウィザード、磨きこみ層）が可視化された
3. **最終決定**: setup-securecheckの手順書740行を実際に読み込み、確定的チャンク/判断の交互構造を発見。install.js相当・scanまで実装・検証完了。setup-localは超精密作業計画ノートとして設計を完全に固めた上で次セッションに持ち越し
4. **残った課題**: setup-local自体の実装・検証、v3.1.0実装記録ノートの作成、kit/build-kit.jsの要否再判断（個別磨きこみ完了後）

### 次のセッションに引き継ぐべき「空気感」

- **このプロジェクトの優先順位**: 「AIに任せる」のではなく「コードに任せてAIは起動係に縮小する」という一貫した方向性。ただし判断の境界を削りすぎず、AIが現場の予期しない状況に適応できる柔軟さを意図的に残す
- **避けるべきアンチパターン**: 決定事項を鵜呑みにせず、都度「それは今も実在するか」を確認する（フェイルクローズの移設先が実は空箱だった、という実例あり）。込み入った変更は実装前に隔離した一時ディレクトリで非破壊に実機検証してから確定する
- **重視している価値観**: 確定的にできる部分は思い切って一気に進めるが、判断が必要な境界は意図的に残す。ノート同士を密にリンクさせ、後から読む人（AIも人間も）が迷わないようにする
- **現在の開発フェーズ**: setup-securecheck v3.1.0の実装フェーズ、③setup-localが最後の主要ピース
